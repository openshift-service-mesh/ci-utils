# style-review Analysis

## Purpose

`style-review` is one of four review phases in the `code-reviewer` plugin. It performs a **unit-scoped** review of a single review unit, checking the changed code against the project's documented style conventions in `style-guide.md`. It is deliberately narrow: it only flags violations of documented conventions, never personal preferences or linter-enforced rules.

The design principle is **policy-based style enforcement**: if a pattern isn't in the style guide, it can't be a style finding. This makes style-review predictable and fair — engineers know exactly what to expect based on the written conventions.

## Inputs

The skill receives a single argument: the **unit-scoped review brief** for one review unit. The brief contains:
- Changed files and their diffs (scoped to this unit only)
- Commit messages relevant to this unit
- Relevant excerpts from `style-guide.md` (pre-filtered by `triage` for this unit)
- Cross-unit context summary (one sentence per other unit)

The brief is generated by `triage` and is distinct from the full-scope brief used by `adversarial-review`.

## Output Artifacts

The skill produces **stdout-only output** following the structure in `templates/phase-report.md`:

- **Heading**: "Style Review Report — [Unit Name]"
- **Strengths**: Specific patterns done well, with file:line references
- **Issues by severity** (Critical/Important/Minor) with `STY-N` prefixed findings:
  - Each finding: ID, `file:line` reference in backticks, style guide section cited, description, fix
- **`IMP-N` findings**: patterns worth adding to the style guide (not violations)
- **Open Questions**: style situations genuinely not covered by the guide

### Severity Calibration

- **Critical**: Widespread convention violations that would confuse readers or tooling
- **Important**: Isolated but clear violations of documented conventions
- **Minor**: Minor deviations, naming inconsistencies, or edge-case violations

## Out of Scope

The style reviewer explicitly **must not** flag:
- Linter-enforced concerns (import ordering, indentation, trailing whitespace, bracket placement)
- Performance concerns (those belong to adversarial-review)
- Test coverage gaps (those belong to testing-review)
- Bugs or logic errors (those belong to adversarial-review)

## Evaluation Notes

Since the output is stdout-only, all judges use `{{ conversation }}` to access the report. The critical quality signals are:

1. **Style guide citations**: every STY-N finding must cite the guide (not personal preference)
2. **File:line references**: every finding (STY-N and IMP-N) must have a backtick-wrapped `file:line`
3. **No linter scope creep**: import order, whitespace, indentation must not appear as findings
4. **Severity appropriateness**: minor violations must not be Critical

The evaluation dataset should include:
- Code that violates specific documented conventions (true positives)
- Clean code that passes style (no findings expected)
- Code with linter concerns only (must be ignored)
- Code with patterns not in the guide (IMP-N expected)
